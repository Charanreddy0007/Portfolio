How I Built LeetCode Sync

Maintaining a LeetCode GitHub repository manually quickly became repetitive. Every accepted problem required copying the solution, creating folders, updating README files, committing the changes, and pushing everything to GitHub. To eliminate that workflow, I built LeetCode Sync—an automation tool that incrementally synchronizes accepted LeetCode solutions while keeping track of progress using SQLite.

The Problem

Solving problems was the easy part. Keeping the GitHub repository organized wasn't.

  • Copy solution manually
  • Create folder structure
  • Generate README files
  • Commit changes
  • Push to GitHub

Repeating these steps for every accepted submission quickly became tedious, so I decided to automate the entire workflow.

Project Goal

The goal was to build a synchronization pipeline that automatically detects new accepted LeetCode submissions, downloads all required metadata, generates documentation, uploads everything to GitHub, and safely resumes if the process is interrupted.

Key Features

  • Incremental synchronization
  • LeetCode GraphQL integration
  • GitHub REST API integration
  • SQLite state management
  • Automatic README generation
  • Resume after interruption
  • Retry failed operations
  • GitHub Actions automation
  • SHA tracking for updates

System Architecture

The synchronization process follows a staged pipeline. Each stage stores its progress in SQLite before moving to the next step, making the system resilient to failures.

Synchronization Pipeline

Instead of uploading everything at once, the project processes each problem through several well-defined stages.

  1. Fetch solved problems
  2. Download submission details
  3. Retrieve source code
  4. Fetch question metadata
  5. Generate problem README
  6. Upload problem to GitHub
  7. Upload solution
  8. Update root README

State Management with SQLite

Every synchronization stage updates a status value inside SQLite. If the workflow stops unexpectedly, it resumes from the last completed stage instead of starting over. 


Status 1 → Problem Information

Status 2 → Submission Details

Status 3 → Source Code

Status 4 → Question Data

Status 5 → Upload README

Status 6 → Upload Solution

Status 7 → Update Repository README

Failure Recovery

Reliability was one of the primary design goals. Whenever an API request fails, the project records the error, increments a retry counter, and exits safely. The next scheduled execution continues from the last successful checkpoint.

GitHub Actions Automation

GitHub Actions runs the synchronization process automatically every few hours. Each execution processes exactly one pending problem before exiting.

This design keeps workflows short, minimizes API usage, and greatly simplifies recovery after failures.

What I Learned

This project taught me much more than simply interacting with APIs. It demonstrated how state machines, incremental synchronization, database persistence, retry mechanisms, and workflow automation can be combined to build a reliable production-style system.

Most importantly, I learned that reliable automation isn't just about making things automatic—it's about making them recoverable when something goes wrong.

Conclusion

LeetCode Sync transformed a repetitive manual process into a fully automated pipeline. By combining GraphQL, SQLite, GitHub REST APIs, and GitHub Actions, the project continuously synchronizes accepted LeetCode solutions while maintaining consistency and recovering gracefully from interruptions.
